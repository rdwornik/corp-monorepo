## Headline deepenings beyond Phase 1

1. **The effective RFP answer pool is 39 notes, not 182.** Of the 182 `rfp_visible=1` notes, 143 carry `confidence='deprecated'`, and retrieval excludes deprecated by default (`engine.py:208-209`). Stack B's `--rfp-only` path therefore draws on **39 extracted notes** — 12 of which have an empty `products` field. (index.db `mode=ro` query, 2026-07-05: `notes`=488; `rfp_visible=1`=182; of those `deprecated`=143, `extracted`=39.)
2. **Federation is not purely PHANTOM — a lighter variant is built and unit-tested, but dormant.** `rebuild_index` loops `config.index_extra_roots` (`index_builder.py:214-221`); `_index_cke_notes` explicitly handles rfp_kb frontmatter (synthesizes `title` from `id`, `index_builder.py:636-640`); `_compute_rfp_visible` rule 3 says "`verified` trust_level → always (rfp_kb entries)" (`index_builder.py:584,596-597`); `tests/test_index_builder.py:450-498` tests exactly the rfp_kb scenario. The switch — env var `INDEX_EXTRA_ROOTS` (`config.py:100`) — has never been set (index still holds only the 488 vault notes; `meta.last_rebuild` = 2026-03-28). **ADR-22's ratified design (`rfp_entries` table, `corp rfp-index`, grouped display, no cross-corpus score interleaving) remains PHANTOM** — no `rfp_entries`, no `rfp-index` command in `src/`. The built mechanism mixes KB rows into the same `notes` table with interleaved BM25 — the exact thing ADR-22 §"What not to do" rejected as mathematically incoherent. See §5.
3. **The Word agent is BROKEN at startup, not merely untested.** `main()` unconditionally calls `get_family_display_name` → `load_family_config` → `open(data/kb/schema/family_config.json)` (`rfp_answer_word.py:673,114-117`) and `data/` does not exist in the repo → `FileNotFoundError` before any document parsing. Its only test is `--help` (`tests/rfp/test_cli_smoke.py:9-13`), which exits before config load.
4. **A retrieval score-scale mismatch quietly breaks every threshold in Stack B.** The engine returns `relevance_score` = BM25 rank (negative, lower=better) **plus** trust boost `{verified:0, extracted:10, generated:50, draft:100}` (`engine.py:75-90`); `vault_adapter` and the Word agent treat it as a 0–1 higher-is-better similarity. Consequences: within a trust tier the sort order is inverted (`vault_adapter.py:63-68`); `LOW_CONFIDENCE_THRESHOLD = 0.25` (`vault_adapter.py:20,96`) is meaningless; in the Word agent `similarity = score`, so verified/extracted notes (score ≤ 0) can **never** pass `--kb-threshold 0.75` while generated/draft notes (score 10–110) **always** pass (`rfp_answer_word.py:381-385,738-741`). The 0–1 conversion `_bm25_to_score` exists but runs only on the direct-SQLite fallback path (`vault_adapter.py:227,265-277`).
5. **"Generic" Excel runs are silently planning-scoped.** `LLMRouter.__init__` sets `self.family = solution or "planning"` (`llm_router.py:193`), so a run without `--solution` — which prints `Solution: NONE (generic)` (`rfp_excel_agent.py:595`) — product-filters retrieval to `planning`.
6. **The feedback/correction tooling points at a KB representation that does not exist.** `rfp_feedback.py` operates on `data/kb/{verified,drafts,rejected}/<family>/<id>.json` (`rfp_feedback.py:22-26`) — absent. The real KB is `.md` under `corp_data/rfp_kb/`, which **no code reads or writes**: `rfp_kb_path()` (`schema/config.py:87-89`) has zero callers; the only reach mechanism is the unset `INDEX_EXTRA_ROOTS`.
7. **`src/corp/rfp/README.md` misdescribes the module** ("answer_selector ranks" in the data flow; "Used by: corp.cli.rfp, corp.retrieve.rfp") — `answer_selector` has no src caller and `corp.cli.rfp`/`corp.retrieve.rfp` import nothing from `corp.rfp`. Authoritative-looking dead doc, same class as Phase-1 finding #10.

## Step 5 — Federation vs merge: decision inputs

Context that changed since ADR-22 (2026-03-28): `corp-rfp-agent` — which ADR-22 names as "authoritative owner of RFP KB files" and whose ChromaDB it preserved — has been archived into the monorepo; the ChromaDB no longer exists; **the ownership constraint in ADR-22 is stale**. Also: all 1,329 KB files carry the same mtime (2026-03-15), so ADR-22's "label RFP results with file mtime; flag > 18 months `[STALE?]`" would fire uniformly and uselessly — per-entry staleness must come from frontmatter (`last_updated`), not mtime.

### Option (a) Federate at query time — ADR-22 as ratified

| Needs | Detail |
|-------|--------|
| index schema | New `rfp_entries` FTS5 table in index.db (independent rebuild); no change to `notes` |
| indexer | `corp rfp-index` command + normalization adapter (title-synthesis logic at `index_builder.py:636-640` is reusable); `--check` parse validation |
| retrieval | `--source vault\|rfp\|all` flag on `corp retrieve` (default all); grouped display with per-source caps (3 RFP / 5 vault); **no score interleaving** |
| trust semantics | KB results labeled `curated`; vault stays `extracted` — maps onto existing `CONFIDENCE_BOOST` tiers cleanly (`verified`=0 already reserved for KB) |
| `rfp_visible` | Unaffected — separate table sidesteps the 39-note bottleneck for KB content; vault-side pool still needs the deprecated-trust repair regardless |
| frontmatter mapping | Adapter maps KB fields (`id`, `category`, `products`?, `last_updated`, `trust_level`) → `rfp_entries` columns; KB-specific fields (category, question variants, keywords per distiller schema `config/rfp/prompts/kb_distiller_prompt.txt`) get proper homes instead of being dropped |
| dedup vs vault | None needed — sources stay distinct; duplicate *content* across sources shows as two labeled results (ADR-22 accepted this) |
| **Risks** | Build cost is real (M: table + command + flag + display + prep injection); two retrieval contracts to maintain; consumers (Stack B adapter) must learn the grouped shape |

### Option (a′) The built-but-dormant variant — `INDEX_EXTRA_ROOTS` into `notes`

| Needs | Detail |
|-------|--------|
| switch | `INDEX_EXTRA_ROOTS=C:/Users/1028120/Documents/corp_data/rfp_kb` + `corp index rebuild` — **that is all; mechanism is unit-tested** (`tests/test_index_builder.py:450-498`) |
| trust semantics | Rides `_compute_rfp_visible`: `trust_level: verified` → `rfp_visible=1` and boost 0 → the 1,155 verified KB entries would outrank all vault `extracted` notes within any match set — plausibly desirable, but it is an accident of the boost table, not a decision. Caveat: §4.5 shows `verified` over-claims for 97 network/wms files |
| `_staging` handling | Correct by construction: all 174 staging entries carry `trust_level: draft` → excluded from RFP visibility (`index_builder.py:594-595`; §4.4 confirms the 1:1 frontmatter discipline) |
| frontmatter mapping | Lossy: `notes` has no `category` column; title synthesized from `id`; `client` empty (good: KB is client-anonymous); question-variants/keywords dropped |
| dedup vs vault | Safe from mass-deletion: `_dedup_notes_by_hash` skips empty `source_hash` (`index_builder.py:721-724`); KB entries lack `source_hash` → never deduped, also never staleness-checkable by hash |
| **Risks** | **Implements what ADR-22 explicitly rejected** — interleaved BM25 across corpora with different term statistics ("mathematically incoherent", ADR-22 §Alternatives); 1,329 KB rows would dominate a 488-note corpus and shift BM25 IDF statistics for *every* consumer of `corp retrieve`/`corp prep`, not just RFP; using it as-is is an architectural decision by default |

### Option (b) Merge KB into vault as notes

| Needs | Detail |
|-------|--------|
| write path | An ingest lane for KB entries (there is none today — headline #6); ADR-27 single-writer invariant means it must go via `vault_io.write_note()` or a sanctioned `ingest/` path |
| frontmatter mapping | Full KB→note schema mapping (title, products, topics, trust_level, `valid_to` for expiry, source_* provenance); category → topics or a new field; 174 `_staging` entries need triage before or during migration |
| dedup vs vault notes | Real risk of content overlap with the 39 extracted rfp_visible notes and future W2 output; needs a content-hash or answer_selector-style comparison pass (the one thing `answer_selector` was actually built for) |
| `rfp_visible` | Merged entries with `trust_level: verified` become rfp_visible automatically — pool grows from 39 to ~1,200 in one stroke |
| governance | **Directly contradicts ADR-22 §"What not to do" ("Do not migrate RFP KB entries into vault as notes — violates single-source-of-truth")** — requires a superseding ADR, not a quiet build |
| backup | Vault git becomes the KB's only home — and vault git has **no remote** (Phase-1 X1). Merging before X1 is fixed concentrates all irreplaceable data in one unbacked store |
| **Risks** | Sync/reconciliation burden ADR-22 named; corpus inflation 488→~1,800 changes BM25 behavior for all existing workflows; migration is one-way in practice |

**Common to every option** (decide once, applies regardless): (i) per-entry staleness representation — `valid_to` exists in the notes schema and is consumed by nothing; a retrieval-time expiry filter is S; (ii) product-family attribution — resolved in the KB's favor: frontmatter `products` is populated and consistent with directory family across the sample (§4.2), so product scoping survives any option; (iii) the vault-side trust repair (143 deprecated rfp_visible notes) is needed under all options.

## Step 6 — Guardrails and style-store readiness

### Where `forbidden_claims` / product profiles / `overrides.yaml` would hook — exact seams

**Blocker to note honestly:** profile lookup is keyed by family code, and family identity is inconsistent across stacks — Excel silently defaults to `planning` (headline #5), Word requires `--family`, Stack A has a freeform `--product` with no family concept. A family-normalization shim precedes any profile gating.

### Style-store readiness of KB entries

The distiller that produced the KB emitted style-relevant structure: `canonical_question`, `canonical_answer`, `question_variants`, `keywords`, `last_updated`, `sources_used` (`config/rfp/prompts/kb_distiller_prompt.txt`). What survives in the `.md` corpus frontmatter is reported in Step 4. What the target style store needs that **nothing** currently carries: answer length/register/tone tags, category-of-form (boilerplate vs technical-spec vs commitment), accept/edit/reject provenance, product-agnostic form markers. The `notes` schema offers `topics/products/domains/quality/valid_to` but no category or style fields.

### Stage-7 capture point today

**None persisted.** The Word `--interactive` loop captures accept/edit/skip decisions in control flow and discards them (`rfp_answer_word.py:564-614` — accepted blocks go to the doc, decisions go nowhere). The Excel path has no review at all. The only feedback writer in the estate, `append_feedback_log` → `data/kb/feedback_log.jsonl` (`rfp_feedback.py:124-134`), is invoked solely by the KB-correction command, targets an absent directory tree, and has no reader in `src/` (Phase-1 §1.3, re-confirmed). Wiring `interactive_review` decisions into that writer (with a real schema and home) is the single cheapest stage-7 seed.
